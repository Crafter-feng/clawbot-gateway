# ClawBot Gateway 前端界面设计文档

## 设计概述

基于 DESIGN.md 和 AGENTS.md 的核心规则，重新设计前端界面，重点增强路由规则系统。

## 设计原则

1. **简洁清晰**：操作直观，信息层次分明
2. **功能完整**：覆盖所有后端功能
3. **响应式**：支持桌面端和移动端
4. **可访问性**：支持键盘操作和屏幕阅读器

## 路由规则系统设计

### 数据模型

#### 规则条件

```typescript
// 单个匹配条件
interface RouteCondition {
  id: string                  // 条件 ID（前端生成）
  field: ConditionField       // 匹配字段
  operator: ConditionOperator // 匹配操作符
  value: string               // 匹配值
  case_sensitive: boolean     // 是否区分大小写
}

// 匹配字段
type ConditionField = 'message' | 'from_user' | 'to_user' | 'msg_type'

// 匹配操作符
type ConditionOperator = 
  | 'exact'        // 精确匹配
  | 'contains'     // 包含
  | 'starts_with'  // 前缀
  | 'ends_with'    // 后缀
  | 'regex'        // 正则表达式

// 匹配字段选项
const CONDITION_FIELDS: { value: ConditionField; label: string }[] = [
  { value: 'message', label: '消息内容' },
  { value: 'from_user', label: '发送者' },
  { value: 'to_user', label: '接收者' },
  { value: 'msg_type', label: '消息类型' },
]

// 匹配操作符选项
const CONDITION_OPERATORS: { value: ConditionOperator; label: string }[] = [
  { value: 'exact', label: '等于' },
  { value: 'contains', label: '包含' },
  { value: 'starts_with', label: '以...开头' },
  { value: 'ends_with', label: '以...结尾' },
  { value: 'regex', label: '正则匹配' },
]
```

#### 规则组（支持且/或/非逻辑）

```typescript
// 规则组 - 支持 AND/OR/NOT 逻辑
interface RouteRuleGroup {
  id: string                  // 组 ID
  logic: 'and' | 'or'        // 组内条件的逻辑关系
  conditions: RouteCondition[] // 条件列表
}

// 路由规则
interface RouteRule {
  id: number
  name: string                // 规则名称
  backend_id: string          // 目标后端
  priority: number            // 优先级（数字越小优先级越高）
  enabled: boolean            // 是否启用
  description?: string        // 规则描述
  
  // 规则条件组合
  groups: RouteRuleGroup[]    // 规则组列表
  group_logic: 'and' | 'or'  // 组之间的逻辑关系
  
  created_at: string
  updated_at: string
}

// 条件支持取反
interface RouteCondition {
  id: string
  field: ConditionField
  operator: ConditionOperator
  value: string
  case_sensitive: boolean
  negate: boolean             // 是否取反（非逻辑）
}
```

### 逻辑运算说明

| 逻辑 | 符号 | 说明 | 示例 |
|------|------|------|------|
| AND (且) | `&&` | 所有条件必须满足 | 消息包含"天气" AND 发送者是"admin" |
| OR (或) | `\|\|` | 任一条件满足即可 | 消息包含"天气" OR 消息包含"预报" |
| NOT (非) | `!` | 条件不满足时生效 | NOT 消息包含"测试" |

**组合示例**：
```
(消息包含"天气" OR 消息包含"预报") AND NOT 消息包含"测试"
= ((消息包含"天气") OR (消息包含"预报")) AND (NOT 消息包含"测试")
```

### 规则组合逻辑示例

#### 示例 1：简单规则（单条件）
```
消息包含"天气" → 转发到 hermes
```

#### 示例 2：AND 逻辑（所有条件必须满足）
```
消息包含"天气" AND 发送者是"wxid_admin" → 转发到 hermes
```

#### 示例 3：OR 逻辑（任一条件满足）
```
消息包含"天气" OR 消息包含"预报" → 转发到 hermes
```

#### 示例 4：NOT 逻辑（排除条件）
```
NOT 消息包含"测试" → 转发到 hermes
（排除包含"测试"的消息）
```

#### 示例 5：混合逻辑（且/或/非组合）
```
(消息包含"天气" OR 消息包含"预报") AND NOT 消息包含"测试"
= ((消息包含"天气") OR (消息包含"预报")) AND (NOT 消息包含"测试")
→ 转发到 hermes
```

#### 示例 6：正则 + 条件组合
```
消息匹配正则 /^\/help.*/ AND 消息类型是文本 → 转发到 echo
```

#### 示例 7：发送者过滤
```
发送者是"wxid_admin" OR 发送者是"wxid_test" → 转发到 echo
（只处理特定发送者的消息）
```

#### 示例 8：消息类型过滤
```
消息类型是"图片" AND NOT 消息包含"测试" → 转发到 relay
（处理图片消息，但排除测试消息）

### 路由规则功能

#### 1. 匹配字段

| 字段 | 说明 | 示例 |
|------|------|------|
| `message` | 消息内容 | "今天天气怎么样" |
| `from_user` | 发送者 ID | "wxid_xxx" |
| `to_user` | 接收者 ID | "wxid_yyy" |
| `msg_type` | 消息类型 | "text", "image", "file" |

#### 2. 匹配操作符

| 操作符 | 说明 | 示例 |
|--------|------|------|
| `exact` | 精确匹配 | "天气" 只匹配 "天气" |
| `contains` | 包含匹配 | "天气" 匹配 "今天天气怎么样" |
| `starts_with` | 前缀匹配 | "天气" 匹配 "天气预报" |
| `ends_with` | 后缀匹配 | "天气" 匹配 "查天气" |
| `regex` | 正则匹配 | `/help.*` 匹配 "help me" |

#### 3. 逻辑组合

| 逻辑 | 说明 | 示例 |
|------|------|------|
| `AND` (且) | 所有条件必须满足 | 消息包含"天气" AND 发送者是"admin" |
| `OR` (或) | 任一条件满足即可 | 消息包含"天气" OR 消息包含"预报" |
| `NOT` (非) | 条件不满足时生效 | NOT 消息包含"测试" |

**组合示例**：
```
(消息包含"天气" OR 消息包含"预报") AND NOT 消息包含"测试"
= ((消息包含"天气") OR (消息包含"预报")) AND (NOT 消息包含"测试")
```

#### 4. 优先级

- 数字越小优先级越高
- 相同优先级按创建时间排序
- 匹配时从最高优先级开始，第一个匹配的规则生效

#### 5. 启用/禁用

- 可以临时禁用规则而不删除
- 禁用的规则不参与匹配

#### 6. 正则表达式安全

- 长度限制：200 字符
- 禁止嵌套量词（如 `(a+)+`）
- 执行超时：100ms
- 提供实时预览和测试

### 路由匹配流程

```
用户消息
    ↓
┌─────────────────────────────────────────────┐
│ 1. 检查用户会话级覆写（/use 设置）            │
│    如果有 → 使用覆写的后端                    │
└─────────────────────────────────────────────┘
    ↓ (无覆写)
┌─────────────────────────────────────────────┐
│ 2. 按优先级遍历路由规则                       │
│    - 检查规则是否启用                         │
│    - 根据匹配类型检查消息                      │
│    - 第一个匹配的规则生效                      │
└─────────────────────────────────────────────┘
    ↓ (无匹配)
┌─────────────────────────────────────────────┐
│ 3. 使用默认后端                              │
└─────────────────────────────────────────────┘
    ↓
使用匹配到的后端处理消息
```

## API 端点设计

### 路由规则 API

| 端点 | 方法 | 说明 |
|------|------|------|
| `/api/v1/routes` | GET | 列出所有路由规则 |
| `/api/v1/routes` | POST | 创建路由规则 |
| `/api/v1/routes/:id` | GET | 获取单个路由规则 |
| `/api/v1/routes/:id` | PUT | 更新路由规则 |
| `/api/v1/routes/:id` | DELETE | 删除路由规则 |
| `/api/v1/routes/:id/toggle` | PUT | 切换启用/禁用状态 |
| `/api/v1/routes/reorder` | PUT | 重新排序路由规则 |
| `/api/v1/routes/test` | POST | 测试路由匹配 |

### 路由规则请求/响应格式

**创建/更新请求**：
```json
{
  "keyword": "天气",
  "backend_id": "hermes",
  "match_type": "exact",
  "priority": 1,
  "enabled": true,
  "description": "天气查询"
}
```

**列表响应**：
```json
{
  "routes": [
    {
      "id": 1,
      "keyword": "天气",
      "backend_id": "hermes",
      "match_type": "exact",
      "priority": 1,
      "enabled": true,
      "description": "天气查询",
      "created_at": "2026-07-26T13:48:32Z",
      "updated_at": "2026-07-26T13:48:32Z"
    }
  ]
}
```

**测试匹配请求**：
```json
{
  "message": "今天天气怎么样",
  "user_id": "wxid_xxx"
}
```

**测试匹配响应**：
```json
{
  "matched": true,
  "rule_id": 1,
  "backend_id": "hermes",
  "match_type": "exact",
  "matched_by": "keyword"
}
```
